# Knowledge Intake Protocol

## 目的

定义后续批量更新知识库时，用户应该如何把待处理材料交给 Codex，以及 Codex 默认应如何处理。

## 推荐交付方式

每次更新时，给 Codex 一个待处理目录。

这个目录里建议包含两类内容：

1. 待处理文件
2. 一份说明文件，建议命名为 `intake.md`

Codex 再根据说明文件和仓库规则，判断哪些内容进入对应产品仓库的 `raw/`、`drafts/`、`workspace/`、`context/`，以及是否需要进入独立的 `kb-publish` 发布流程。

## 推荐目录形态

```text
<incoming-folder>/
|- intake.md
|- file-1.ext
|- file-2.ext
`- subfolders/
```

如果材料较多，也可以按主题分子目录，但仍建议在根目录保留一份 `intake.md`。

## `intake.md` 最小字段

建议至少写清这些信息：

```markdown
# 材料导入说明

- 批次名称：2026-04 AI单证历史资料整理第一批
- 归属产品：ai-recog
- 材料类型：product-materials
- 时间范围：2025-01 ~ 2026-04
- 来源：产品经理个人沉淀资料 + 历史评审材料导出
- 目标：归档原始资料，并提炼产品现状、模块边界和高频 FAQ
- 敏感级别：公开内部
- 期望产出：优先补 raw 和 context，如材料足够稳定则补充 kb-publish
- 补充说明：这批材料以历史存量为主，版本细节较杂，优先提炼稳定结论；涉及客户名的材料不要直接发布到 kb

## 文件说明

| 文件或目录 | 简要说明 | 可选提示 |
|---|---|---|
| AI单证产品介绍V3.pptx | 当前对内产品介绍材料 | 可作为产品概览来源 |
| ERP对接需求梳理.docx | 历史需求梳理文档 | 可能适合先进入 drafts |
| 2025项目申报材料/ | 过往项目申报资料目录 | 先归档 raw，再判断是否提炼案例 |
| FAQ收集.xlsx | 日常问题汇总 | 可提炼为 FAQ 草稿 |

## 可选路由备注

- 明确不要进入 `kb-publish` 的文件：包含客户名称、报价或项目敏感信息的申报材料
- 只应作为来源材料处理的文件：原始导出的 PPT、Excel、PDF
- 已经足够稳定、可进入 `context` 的文件：产品介绍、稳定模块说明、通用业务流程说明
```

字段说明：

- `批次名称`：本次材料包名称
- `归属产品`：归属产品；如果跨产品就写 `cross-product`
- `材料类型`：例如 `product-materials`、`projects`、`faq`、`reference`
- `时间范围`：材料对应时间
- `来源`：来源人、来源系统或来源场景
- `目标`：这批材料希望支持什么整理目标
- `敏感级别`：公开内部、限产研、限项目组、敏感
- `期望产出`：如果你已经知道想更新到哪层，可以写在这里；不知道可以留空
- `补充说明`：其他补充说明

建议做法：

- 模板里默认保留一份示例内容
- 实际使用时，直接在示例上改写，不需要先清空再填写
- `文件说明` 至少写到文件夹级或关键文件级，这样 Codex 更容易判断路由

## 最推荐的用户指令格式

```text
请处理这个待整理目录并更新知识库：

目录：D:\path\to\incoming-folder
目标：归档来源材料，并提炼可进入 context / kb-publish 的内容
要求：
1. 你自己判断 raw、drafts、workspace、context、kb 的去向
2. 不要漏掉来源归档
3. 更新对应 AGENTS.md
4. 最后汇报新增和更新了哪些文件
```

如果你已经知道偏向，也可以补一句：

```text
这批材料主要是历史存量资料，优先走 raw -> drafts -> context
```

或者：

```text
这批材料主要是当前版本材料，优先判断 workspace 和 context
```

## Codex 的默认处理逻辑

收到一个待处理目录后，默认按下面的顺序执行：

1. 读取 `intake.md`
2. 扫描目录里的文件和子目录
3. 判断每个文件是原件、整理稿、正式工作文档还是稳定知识
4. 先完成来源归档
5. 再补必要的整理稿
6. 再判断是否需要沉淀到 `context/`
7. 最后判断是否有内容应发布到 `kb-publish`
8. 同步更新相关 `AGENTS.md`

## 路由判断规则

- 原始附件、导出文件、PPT、PDF、Excel、原型导出、原始 FAQ 记录 -> `raw/`
- 归纳稿、总结稿、问答草稿、能力对比、边界判断稿 -> `drafts/`
- 进行中的正式版本文档、当前项目文档、活动需求文档 -> `workspace/`
- 已确认的产品规则、稳定流程、产品边界、长期有效总结 -> `context/`
- 面向外部或统一发布的稳定答案、FAQ、产品说明、流程说明 -> `kb-publish`

## 关于“由你来判断去向”

这是推荐模式。

原因：

- 用户通常更清楚材料背景，但不一定需要亲自做每层路由判断
- Codex 可以基于仓库规则完成分层和归档，减少人工判断成本
- 这样更容易保持结构一致

## 什么时候需要用户显式指定

以下情况建议用户直接额外说明：

- 某批材料虽然是原始文件，但不希望进入 `raw/`
- 某个 FAQ 虽然看起来稳定，但暂时不要发布到 `kb-publish`
- 某个版本包虽然已结束，但还不想沉淀到 `context/`
- 材料涉及敏感信息，需要限制使用范围

## 最终建议

默认采用这种协作方式：

- 用户提供一个待处理目录
- 目录中包含文件和一份 `intake.md`
- Codex 负责判断路由、归档、提炼、更新索引

这比让用户逐个指定文件去向更稳，也更省操作成本。
